# Product SKU Matrix

A **SKU** here is a `core/include/*_config_pkg.sv` (plus the build-platform
`soc.coreConfig` that selects it). Features are opt-in; empty cells mean
“typically off / not the product intent,” not “impossible to set by hand.”

Re-check package sources before tape-out claims — this matrix is a **navigation
aid**, not a formal datasheet.

\*Deep-spec package details: open the package; not every deep-spec knob implies OoO.

**OoO packages and the legality guards.** `config_pkg::check_cfg` gates OoO on
speculation support and refuses FP residency outright, because `core/ooo/**` has
no floating-point register class — FP results are neither renamed nor tracked in
the busy table, so the combination *aliases* rather than under-performs:

```
assert (!(Cfg.OoOEn && !Cfg.SpeculativeSb));
assert (!(Cfg.OoOEn && Cfg.NrHarts > 1 && Cfg.FpPresent && !Cfg.SmtDrainedHandoff));
                                                            // FP + mixed residency: refused
`ifndef G6LC_OOO_FP_QUALIFY
assert (!(Cfg.OoOEn && Cfg.FpPresent && Cfg.NrHarts > 1 && !Cfg.SmtDrainedHandoff));
                                                            // single-hart and drained FP lifted (T9g/M4)
`endif
```

Integer multi-hart OoO is **legal** under the drained handoff
(`SmtDrainedHandoff`): the thread selector switches only when the scoreboard and
store queues are empty, so the hart-blind backend never interleaves two harts'
work. Since T9g/M4 the same drained handoff legalizes multi-hart FP — only one
hart is resident in IQ/ROB/LSQ at a time and the FP rename maps, pools and
`dirty_fp_state` are per hart (owner-lifetime proof + four-hart directed test +
Spike-exact FP suite). FP under **mixed** residency stays refused behind
`G6LC_OOO_FP_QUALIFY` (the hart-tagged lazy-FS audit is the remaining work), and
`g6lc64_ooo_server` stays an opt-in/unqualified target. `g6lc64_ooo` sets
`RVF=RVD=1` and is legal single-hart FP; `g6lc64_ooo_int2_l3` is RV64GC+B.
`g6lc64_ooo_int` clears every FP format and keeps `NrHarts=1`; it is a
**verification and bring-up baseline, not a qualified product** — no
independent-reference comparison and no boot evidence. `g6lc64_smt2_ooo_int`
carries the production drained-handoff badge (strictDual OpenSBI/HSM profile).
See `architecture/out-of-order/README.md`.

## How to select a SKU

```ts
// .config.ts
export default defineBuildConfig({
  soc: { coreConfig: 'g6lc64_server_math' },
})
```

```bash
g6lc-build config
g6lc-build verify --lint --target g6lc64_server_math
```

Board overlays (`g6lc-build mb select`) may pin `soc.*` — prefer board contracts
over fighting the overlay.

## Verification cost ladder

| SKU class | Default verify | Optional suites |
|---|---|---|
| Classic imafdc | In default targets | Open-source smoke |
| SMT2 | Opt-in target | `smt-linux-*` |
| OoO lite / server | Opt-in target | `ooo-l3-tests`, `mc-*` |
| Server math | Opt-in target | `server-math-tests` |
| Server math + V | Opt-in + Ara flist | `testlist_ara_vector`, live Ara env |

Optional suites are often excluded from default CI for **runtime**, not maturity.

## Structural timing

Wider issue, OoO, and multi-core hubs raise FO4 risk. Use
[`g6lc-build timings`](../build-platform/timings) for early structural feedback;
STA remains sign-off.
