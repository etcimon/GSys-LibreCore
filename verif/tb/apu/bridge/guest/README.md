# Stock-guest Venus acceptance gate

Boots an **unmodified** Ubuntu 24.04.5 preinstalled riscv64 cloud image
on the `g6lc` QEMU machine against the verilated LibreCore APU bridge
server (`../build-bridge.sh`), then drives the Vulkan acceptance
programs inside the guest over a serial console. Zero firmware, zero
custom driver: the guest's stock `virtio-gpu` kernel driver + Mesa Venus
talk to the RTL through the QEMU `apu-bridge` device.

## Usage

    ../run-guest.sh [--out DIR] [--venus-only] [--skip-provision]

or directly:

    GUEST_CACHE=.cache/apu-guest python3 drive_guest.py [--venusoff] \
        [--boot-only] [--timeout S] [--out DIR]

Environment: `CVA6_REPO_DIR`, `G6LC_QEMU`, `G6LC_QLIB`, `GUEST_CACHE`
(default `<repo>/.cache/apu-guest`), `APU_BRIDGE_OUT` (bridge objdirs),
`G6LC_SOCKDIR` (unix sockets — must be a Linux-native fs, DrvFs cannot
bind them), `G6LC_SKIP_APT` (skip apt when the image already carries
the packages).

## Guest image

- URL: `https://cdimage.ubuntu.com/ubuntu/releases/24.04.5/release/ubuntu-24.04.5-preinstalled-server-riscv64.img.xz`
- sha256: `1cbd4b187f33356107daa637a5588d8f8a1744c7a012189e9c5e6d0b177825c4`
- Expanded to 11 GiB raw (`qemu-img resize`); `vmlinuz` is extracted
  from the rootfs partition with `debugfs` (no root needed). The initrd
  is *not* used — the g6lc machine's 32 MiB aperture hole leaves too
  little low DRAM for it, so the kernel's built-in
  virtio_blk/virtio_mmio/ext4 mount the rootfs directly.
- Observed package versions (apt at run time):
  `mesa-vulkan-drivers 25.2.8-0ubuntu0.24.04.x`,
  `vulkan-tools`/`libvulkan1 1.3.275.0`, `linux-image-7.0.0-31-generic`.

## Payload (cidata, label `CIDATA`)

`cloud-init/{user-data,meta-data}` — NoCloud seed that sets the
`ubuntu` password. `vkcompute.c`, `vkdescarr.c`, `vkmem.c`,
`vkimage.c`, `expected.json`, and
`bufcopy.spv`/`descarr.spv`/`vkimage.spv` (copied at
provision time from `corev_apu/apu/tools/shader/corpus/`).

`expected.json` is generated by the oracle
`corev_apu/apu/tools/shader/spirv_model.py` for `bufcopy.spv`
(`out[i]` words, hex); regenerate it when the shader changes.

## What PASS means

- `vulkaninfo --summary` lists the Venus GPU
  (`driverName = venus`, `deviceName = Virtio-GPU Venus (LibreCore …)`).
- `vkcompute bufcopy.spv` → `G6LC_VKCOMPUTE_PASS words=32` — dispatch
  output bit-exact vs `expected.json` (checked inside the program).
- `vkdescarr descarr.spv` → `G6LC_VKDESCARR_PASS words=32` — dynamic
  descriptor-array indexing (`shader*ArrayDynamicIndexing` enabled).
- `vkmem` → `G6LC_VKMEM_PASS` — 12 MiB host-visible alloc+map+verify,
  2 MiB device-local alloc+bind, and the 12 MiB device-local negative.
  The negative runs under `VN_PERF=no_async_mem_alloc` (set inside
  vkmem.c): Venus submits `vkAllocateMemory` asynchronously and returns
  `VK_SUCCESS` unconditionally, so a renderer-side OOM is only
  observable synchronously with Mesa's documented no-async knob.
- `vkimage vkimage.spv` → `G6LC_VKIMAGE_PASS words=64` — §12.3 C/5b:
  format-properties truthfulness (D32_SFLOAT zero features,
  R8G8B8A8_UNORM exactly the generated set), 4x4 RGBA8 upload via
  staging + `vkCmdCopyBufferToImage`, compute `textureLod` bilinear at
  fractional coords with CLAMP_TO_EDGE and REPEAT samplers writing an
  rgba32f storage image, `vkCmdCopyImageToBuffer` readback vs a CPU
  reference (abs tolerance 4/255), plus the D32_SFLOAT
  `vkCreateImage` negative arm.  The readback buffer is mapped
  *before* the submit: host-visible memory is lazy-backed (backing is
  established only by MAP_BLOB at vkMapMemory), so a GPU copy into
  still-unbacked memory is refused truthfully with DEVICE_LOST —
  persistent mapping is the recommended real-world pattern anyway.
- `--venusoff` run: `vulkaninfo --summary` must show *no* Venus device
  (llvmpipe-only control).
- The driver prints `GUEST-PASS` / `GUEST-FAIL` last; `run-guest.sh`
  exits non-zero unless every run printed `GUEST-PASS`.

Wall time: dominated by TCG boot + apt. ~10–25 min per boot on a
reasonably fast host; `G6LC_SKIP_APT=1` drops most of it once the image
has been provisioned once (packages persist in the expanded image).
