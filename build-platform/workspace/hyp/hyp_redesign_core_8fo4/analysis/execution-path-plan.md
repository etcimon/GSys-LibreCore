## 1. Correction to the record (T9 — the instrument changed the conclusion)

The r30 log attributes the r13 stop to "a frontend/fetch-side starvation boundary" because "ITI fetch trace ALSO ends at 0x8000ea9a — the csrrw was never fetched". The ITI in this tree is `corev_apu/instr_tracing/ITI/g6lc_iti/{block_retirement,single_retirement,itype_detector}.sv`, driven by `uop_entry_i` from the **commit** side: it is a retirement trace, not a fetch trace. RVFI and ITI ending at the same PC is one observation seen twice (P4: repeated views are not independent support). The attribution "never fetched" is therefore **unsupported**, and the proposed next step (windowed `+fe_trace` around a cycle that would first have to be found by a second full run) was built on it.

Co-factor probe (P2, cheap): count earlier `csrrw rd≠x0, mtvec` retirements in the r13 RVFI trace. If dozens retired, "CSR write to mtvec with rd==rs1" alone is not the class; the straddle/line-boundary or the surrounding sequence is a co-factor.

**Result (2026-10-23, `hyp8-osbi-scalar-r13-hang`, `r14xp`).** H-CSR survives, H-FE and H-RL are dead: the hang dump shows the SB head `slot=22 issued=1 valid=0 fu=CSR pc=0x8000ea9e`, the frontend idle and run-ahead (`head pc=0x8000eb5e`, lbuf inactive), and the CSR table full with two **younger** CSRs — `buf[0] tid=23 addr=0xda0`, `buf[1] tid=5 addr=0xc01` — both allocated with `cmask=0` and `csr_ready_i=1` at IRO ack, forty cycles apart, while tid 22 (operand-stalled) never reached IRO. Earlier mtvec writes (`0x8000ea70`, `0x8000ea78`) retired normally, so rd==rs1/mtvec is not the class. The class is a **resource released in commit order but allocated in issue order** (H1 lift: W2 trap-probe loops are dense in CSR ops, which is why it surfaces in `sbi_hart_init`): the two-entry table fills with younger CSRs, the oldest cannot allocate, commit cannot advance, and `csr_ready` never returns. H-LEAK (unqualified cancelled arrival) and H-CREDIT (two acks against one entry) were refuted by the `+csrtab_trace` run; the leak qualification and owner-liveness release were kept as leaf-proven hardening (r32). The IQ rule N1d (`g6lc_iq_legal` CSR frontier) should have forbidden the younger issues; why it did not is the r33 STEP-1 question (X-FRONT vs X-BLIND in the brief), and it matters beyond CSRs because the same frontier mechanism carries T24 store ordering. The structural repair (r33) allocates the table entry at **dispatch** in program order, which makes the inversion impossible by construction instead of relying on the frontier filter.

**External-edit attribution (r31/r32 A/B).** The eight externally edited files carry both the witness advance (r14/r15 pass 0x8000ea9e, r14x/r15x reproduce the wedge bit-for-bit) and the h33 store-forward livelock (r32a and r32b each still fail: both the LSU-credit group and the OoO group independently carry a sufficient fault). The advance is a timing coincidence on the inversion, not a repair; the owner is the admission order.

## 2. New findings this pass

**F11 — loop-buffer inject identity (frontend, contract violation, provable).** `frontend/g6lc_loop_buffer.sv:233-254`: `hit_q`/`hit_data_q` are captured at `seq_hit` for the FTQ head present that cycle; `consume_o = hit_q && lookup_ready_i` never re-checks that the head being injected into is the same head/epoch. `fetch_B/frontend.sv:945-963` presents the inject as an I$ response for `ftq_head_vaddr` (the *current* head). The lbuf flush (`frontend.sv:603`) omits `reseed_now`, while the FTQ and FDIP flushes include it (`:547`, `:577`). A flush/reseed between detection and consume therefore delivers the OLD block's bytes under the NEW head address — the I$→realign promise "the bytes I hand you are the bytes at this address" is broken, exactly the shape of the r8 "wrong-path skip, control landed mid-handler" family. `seq_hit` also does not require the head to be valid. Fix by identity (r31): register `hit_vaddr_q`/`hit_epoch_q`, require `lookup_valid_i && lookup_vaddr_i == hit_vaddr_q && hit_epoch_q == epoch_i` for `hit_live`/`consume_o`/`active_o`, drop a stale hit so demand resumes, flush dominates detection, add `reseed_now` to the lbuf flush, and a translate_off assertion `consume_o |-> identity`. Leaf `tb_g6lc_hyp8_control` section `lbuf` with the `G6LC_MUT_LBUF_STALE_HIT` mutant as the negative control. This is a contract fix independent of whether it is the r13 cause (T7: it is wrong for a program nobody wrote); it must not be credited with the r13 stop unless the dump says H-FE and the r31 witness passes that point.

**F12 — in-flight external edits lack their contracts (H2).** Reviewed against the r30 closure:
- `lsu_bypass.sv` depth 2→4 with `count_o`, and IRO `lsu_full = !lsu_ready_i || (count + |lsu_valid_q| + lsu_pipe_q) >= 4`: the "reservation before state update" pattern (PL-P2) — the two AGU-shadow grants are now counted explicitly instead of enforced by 2-cycle spacing (r20). Sound if (a) at most one LSU grant per cycle (the relaxed gating keeps "a second memory op stays blocked"), (b) the shadow is exactly two edges (`lsu_valid_q`, then `lsu_pipe_q <= |lsu_valid_q`), (c) a killed grant in the shadow over-counts (conservative). Unasserted invariant carried from the depth-2 code: `if (pop_ld_i && pop_st_i) mem_n = '0` clears *all four* slots while the count drops by two — unreachable today (one head, one fu) but now data-losing if ever reached; needs an L3 assertion `!(pop_ld_i && pop_st_i)`.

The soft-ladder throttle it replaces was recorded as "intentional until precise WAW dual-WB is proven". Under WbReserve the FLU lanes are reserved at acceptance (`g6lc_flu_reserve`), the LSU WB lane is separate, so the WB collision class is covered *if* `ex_stage` selects `lsu_data` from the granting port (`|lsu_valid_i` is OR-reduced; the `fu_data` select must follow the port). Required leaf (not present): `tb_g6lc_hyp8_issue` section with an ALU on port 0 and a load on port 1 in one cycle, checking the LSU request carries port 1's operands/TID and the ALU result retires on its own lane.
- `use_alu2` re-enabled for `LAT_ALU_LOW` on ports ≠0 under WbReserve. `continuation-design.md` ¶13 disabled it because "the primary completion bookkeeping does not implement the secondary ALU's staggered A3 record protocol". That claim is unverified in `g6lc_iq_bank.sv`/`g6lc_iq_arb.sv`/`g6lc_flu_reserve.sv` and `ex_stage` (alu2 → which WB lane, with which TID/generation lifetime?). Until a directed leaf shows ALU2 result + TID + cancellation reaching WB on a non-colliding lane with a concurrent FLU result, this is a capability change without a contract (H2 PARTIAL → treat as **unqualified**; A/B against r30 on the first smoke regression).

The rewritten spec-bcast arm is under `if (1'b0)` — dead code, no behaviour.

## 3. The spine: one retirement event, six channels

Every module in the iteration below is evaluated against the same two artifacts, so that the plan is a lattice rather than a list:

1. **The architectural retirement event** `{valid, tid, generation, hart, instruction, drop, exception, destination class, physical destination, write enables, final write data}` (retirement-plan.md Batch A; landed in r6 as the common-event CSR/commit seam). Architectural maps, PRF mirror wakeup, CSR effects, RVFI, instret, store commit and the ITI all consume this event; anything that infers it from a *newly selected* head (the old delayed-ack echo) is a defect.
2. **The six visibility channels** (P3) walked for every change to squash/flush/forward/restore/leftover/commit: (1) squashed op writes, (2) unsquashed op omits a write, (3) state survives a kill, (4) state killed that was still needed, (5) control from a data value — veto, (6) ordering visible to another hart.

The abstract trace template per file (retirement-plan.md ¶"For every worklist entry") is kept verbatim: reset and disabled-feature branch → offer vs accepted transfer → normal completion → backpressure → simultaneous allocate/free → WB/cancel → commit/flush → replay/refill → ID reuse; for each added register: producer event, stored fields, current owner, consumer event, stale-reuse rule; follow each output to a sequential consumer, an architectural effect, or a documented external handshake.

## 5. Latency bubble-up points and the 8-FO4 program (structural, not physical)

**Honesty gate first (A1, A121, A146).** The 8-FO4 budget is `(1000/5000 MHz × 1000/20 ps) × 0.8 = 8.0` structural FO4 — a 5 GHz nameplate at fo4_ps=20. The delay-v44 calibration fits `calibrated = 0.992×structural + 12.0` for register-launched paths on Nangate45 (21.398 ps/FO4): the launch intercept alone exceeds 8, so **no division of any positive cone can make a register-launched calibrated reading meet 8 under this profile**; the whole-core adjusted/structural ratio is ~3× (A121: 55.7 structural ≈ 176 adjusted). The only coherent reading of "8 FO4" is therefore the *structural model objective for reg→reg cones* used as a screening discipline, with physical closure quoted separately on each platform at its own `fo4_ps`. Any report that says "8 adjusted FO4" on Nangate45 is wrong by construction.

**Rule of accounting (retirement-plan ¶"Latency accounting is per dependency").** For an isolated dependent chain of latency L, OoO cannot do better than one completion per L cycles; the user-named points — `multiplier`, `alu`, `ex_stage`, `g6lc_lsq`, `wt_dcache_wbuffer`, `store_buffer` — are exactly the units whose L is on the dependence path (load-use, store-forward, multiply, ALU full-width) or whose *service* (one grant per cycle, one drain per cycle) bounds throughput regardless of window. Adding a stage to lower FO4 lengthens L; the design must therefore reduce the *work per stage* (A118: remove serial control before adding cycles; PL-P1/P3: partition the represented value, not the wire) and keep L where a forward path or a reservation hides it.

### 5b. Evaluation protocol for reduced-FO4 execution paths (what "analyzed and evaluated" means for every item above)

The §5a table says *what* to change; this section says what evidence closes each row. Without it a rewrite could be credited on a structural number alone, which A146/A121 and PL-P4 forbid.

**E1 — Board of record and its reproduction.** Exactly one board decides: `analyze-ghz-rN.json` produced with the same analyzer binary/version string (`delay-v44 ir-v5 correction-v5`), the same file list (`inputs/hyp8-core.f`, 309 files), the same `--param-map`/`--calibration` inputs, `--all-modules --stages --target-mhz 5000 --fo4-ps 20 --budget-margin 0.2`. The exact argv of `analyze-ghz-r1` is **not recorded** in the board directory (the JSON carries `opt` and `versions` but not the command line) — it must be captured into `boards/hyp8-core/analyze-ghz-r1.cmd` before r2 is run, or r2 is not comparable (I11, measurement versions are incomparable; the same holds for inputs). **r50 addendum (map identity is part of the board):** the argv must name `analysis/r44-param-map.json` or its successor — never `inputs/param-map-hyp8.json` (a stale 45-key map lacking the HypCfg stage fields; it measured `g6lc_iq_arb=54.66`/`g6lc_ptw=49.50` against the correct 33.85/35.70) — and the board's `.cmd` header must record the map's sha256 (`r44-param-map.json` = `75d16bc9…30e9`). A board without both is invalid; `analyze-r50.cmd` is the reference form. The per-module clock rule quoted in the report (`max(plain reg→reg, worst in-stage, worst into-stage/(1+window))`, multicycle excluded) is applied by an ad-hoc script today; it becomes a checked-in tool (`build-platform/workspace/build/sv-timing/hyp8-src/inputs/clock_board.py`, MIT) that emits the per-file table and the per-cone before/after diff, so every tier re-run is mechanical and the two tables (report vs r2) are produced by the same code.

**E2 — The per-module clock under-reads the design; the stitched view is part of the evaluation.** The module-local rule drops `in→out` and `reg→out` cones, but those continue into the parent in the same cycle. The board's `cross_module_paths` (426 port-bridged stitches, A57) rank the real single-cycle cones differently from the report: `g6lc_iq.i_legal` child 122.0 + parent 100.7 = **222.7**, `g6lc_iq.i_arb` 33.5 + 100.7 = 134.2, `g6lc_ooo_dispatch.i_iq` 100.7 + 24.0 = 124.7, `g6lc_iq.i_bank` 20.4 + 100.7 = 121.1, `g6lc_mmu.i_shared_tlb` 54.0 + 46.2 = 100.2, `g6lc_mmu.i_ptw` 43.1 + 46.2 = 89.3, `g6lc_lsq.i_release` 34.8 + 51.0 = 85.8, `g6lc_mmu.i_itlb/i_dtlb` 38.5 + 46.2 = 84.7, `g6lc_lsq.i_event` 29.0 + 51.0 = 80.0. A port-bridged sum is an upper bound (the parent's 100.7 is itself an in→out cone through `g6lc_iq`), but the direction is unambiguous: **the IQ complex (`g6lc_iq` → `i_legal`/`i_arb`/`i_bank`/`i_payload`/`i_xbar`), not `g6lc_rename_resolve`, is where the structural clock is set once hierarchy is flattened**, and §5a item 15 (`g6lc_iq_legal` 122 in→out: the per-entry serial-class legality over all entries) is the first item, not a mid-table one. Rule: a row is evaluated on three numbers — module reg→reg/in-stage, the module's in→out/reg→out presentation cone, and the stitched parent sum — and "closed" only when the stitched sum is inside the tier budget or the parent side is shown to be a register (then the stitch is a measurement artefact and the board tool records it as such).

**E3 — Rank-0 rewrites are combinational identities; their execution-path evaluation is equivalence, not tracing.** For each rank-0 item: (i) the reference expression is retained under `translate_off` and compared every cycle (`assert (new == old)`), (ii) the assertion is **reachable** — the leaf prints a fire count (`[equiv] <module>: checked=N`) and N must be nonzero and the inputs must have taken both arms (RT §4.6: a declared assertion is not automatically informative), (iii) a mutant that breaks the rewrite (`G6LC_MUT_<ITEM>`) must fail the leaf, (iv) the touched module's existing leaf is re-run, (v) the smokes run with assertions on. The abstract trace template (§3) is **not** required for rank-0 items — the identity covers every path by construction — which is precisely why rank 0 is cheap and why the rank boundary must be honest: any rewrite that changes a register's enable, a reset value, or a port protocol is rank 1 regardless of how small it looks.

**E4 — Rank-1 items are protocol changes; they get the full execution-path trace.** For each: the abstract trace instantiated (reset/disabled, offer vs accepted, normal, backpressure, simultaneous allocate/free, WB/cancel, commit/flush, replay/refill, ID reuse), the six-channel walk, the ownership table for the new register (producer event, stored fields, owner, consumer event, stale-reuse rule), the `svt-pipe` protocol lines (valid/id/kill/flush/result) so the analyzer sees the stage, a leaf with the new timing (and the retimed expectations named — e.g. item 8's `ARB_TAKE_P0_TID1 +1`), smokes, and one witness. The r33 CSR work is the current instance of this discipline (owner moved from issue to dispatch; strobes, credit, group gate, liveness release, mutant).

**E5 — Latency and area are measured, not asserted.** IPC proxy: the three smoke cycle counts (`h34` 682, `h33` 889 on r30/r31x, `bc` 473–475) and the witness retire count at the 6M budget (`r15` 2,049,766) are the regression gate for every rank-1 item; a rank-0 item must leave them bit-identical. Area: the retained board's cell counts per module (`timings`/mapped board) or, before a mapped run exists, the analyzer's `node_count` delta is recorded in the row (A114 trade-off ledger); items that duplicate arithmetic (5, 11) must show the area column.

**E6 — Package-truth before RTL credit.** When a cone's structural reading disagrees with its gate depth by more than the calibration spread (A146: p25–p75 0.81–1.47 of adjusted/structural on v43), the first artifact is an sv-timing fixture reproducing the over/under-read, not an RTL edit (§2.8 fix-package-first). Item 1's `hi_last` function billing and the `$countones(front - 1)` / variable-shift billings in items 2 and 15 are the first three fixtures to write; a rewrite that only lowers the *model's* number is recorded as a measurement fix, not a timing gain.

**E7 — Gates that must be explicit (today's state).** The L5 smoke gate is currently **2/3** on the tree of record because the external edits own the h33 livelock (both external groups independently, r32a/r32b); the plan proceeds on the firmware witness as the gate while that regression is attributed to its owner, and records h33 as a known external failure on every build until it is fixed or the edits are withdrawn — it is not silently waived.
