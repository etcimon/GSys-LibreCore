Vol I §3.1 — RVWMO Memory Consistency Model

Canonical: specs/riscv-spec.html#memorymodel (source line 6600). Domain: CACHE, RAM, SPEC.

The objective of §3.1 is to fix, at the architectural level, "the values that can be returned by loads of memory" without dictating microarchitecture, and the specification names the chosen model "RISC-V Weak Memory Ordering (RVWMO)" precisely because it "is designed to provide flexibility for architects to build high-performance scalable designs while simultaneously supporting a tractable programming model." The load-bearing normative sentence for any speculative, buffered, or cached implementation is that "code running on a single hart appears to execute in order from the perspective of other memory instructions in the same hart, but memory instructions from another hart may observe the memory instructions from the first hart being executed in a different order"; the corollary is that "multithreaded code may require explicit synchronization," for which "the base RISC-V ISA provides a FENCE instruction," augmented by the Zalrsc/Zaamo atomics and, for stricter ordering, the Ztso extension referenced at #ext:ztso.

Mechanically the model is defined in terms of the global memory order, a total ordering of the memory operations produced by all harts (spec quote below). The specification explicitly scopes itself to regular main-memory operations and states that the interaction of the memory model with I/O memory, instruction fetches (Ziccif), FENCE.I, page-table walks, and SFENCE.VMA is not (yet) formalized; those adjacent behaviors are carried in their own sub-files. In CVA6 the model is upheld not by a single block but by the composition of in-order commit and an ordered store path: architectural store visibility is deferred to core/commit_stage.sv:188-192 (commit_lsu_o only when the LSU is ready), the speculative-to-commit queue in core/store_buffer.sv:56-71,110-116,137-167 and the write-through drain in core/cache_subsystem/wt_dcache_wbuffer.sv:52-107,259-280,420-427 release stores in program order, FENCE/FENCE.I are sequenced through core/controller.sv:121-173,257-259 (fence_active_q, fence_i_active_q, halt_frontend_o), and atomics/LR-SC flow via core/amo_buffer.sv:50-63, core/store_unit.sv:134-135,282-319, core/load_store_unit.sv:728-748, plus the WT miss-unit backoff core/cache_subsystem/wt_dcache_missunit.sv:334-347,576-583 and AXI adapter core/cache_subsystem/wt_axi_adapter.sv:252-267,577-580. This connects RVWMO to the speculation guide (misspeculated loads must never leak a globally-inconsistent value) and to the cache guide (any added L2 must preserve this same global order).

Spec quotation

"This section defines the base RISC-V memory consistency model. A memory
consistency model is a set of rules specifying the values that can be
returned by loads of memory. RISC-V uses a memory model called RISC-V
Weak Memory Ordering (RVWMO) which is designed to provide flexibility
for architects to build high-performance scalable designs while
simultaneously supporting a tractable programming model. Under RVWMO,
code running on a single hart appears to execute in order from the
perspective of other memory instructions in the same hart, but memory
instructions from another hart may observe the memory instructions from
the first hart being executed in a different order. Therefore,
multithreaded code may require explicit synchronization to guarantee
ordering between memory instructions from different harts."
(specs/riscv-spec.html:6600-6621, anchor #memorymodel)

Pseudo-SystemVerilog synthesis notes

The skeleton an implementation must provide is an ordered release point plus fence gating and reservation tracking, cross-referenced to the CVA6 loci above:

module rvwmo_order_point #(parameter int unsigned StoreBufDepth)(
  input  logic        commit_store_i,   // core/commit_stage.sv: only committed stores are released
  input  fence_t      fence_i,          // pred/succ sets; sequenced by core/controller.sv
  // stores leave in program order -> global memory order
  output logic        store_release_o,  // core/store_buffer.sv, wt_dcache_wbuffer.sv
  // LR sets reservation; SC succeeds iff reservation still valid (Zalrsc)
  input  logic        lr_valid_i, sc_req_i,
  output logic        sc_success_o      // core/load_store_unit.sv + D$
);
  // invariant: no younger memory op may be globally ordered before an
  // older one except where RVWMO preserved-program-order permits.
endmodule
