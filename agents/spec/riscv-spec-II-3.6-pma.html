Vol II §3.6 — Physical Memory Attributes (PMA)

Canonical: specs/riscv-spec.html#pma (source line 75927). Domain: RAM, CACHE.

The purpose of §3.6 is to give every region of the physical address map a declared set of capabilities, since some memory regions might not support reads, writes, or execution; some might not support subword or subblock accesses; some might not support atomic operations; and some might not support cache coherence or might have different memory models. The specification terms these properties and capabilities of each region of the machine's physical address space physical memory attributes (PMAs). PMAs are inherent properties of the underlying hardware and rarely change during system operation; unlike PMP, PMAs do not vary by execution context. This is the memory-map contract a RAM bring-up and any cache addition must respect, because it decides which regions are cacheable, idempotent, and atomic-capable.

Spec quotation

"The physical memory map for a complete system includes various address
ranges, some corresponding to memory regions and some to memory-mapped
control registers, portions of which might not be accessible. Some
memory regions might not support reads, writes, or execution; some might
not support subword or subblock accesses; some might not support atomic
operations; and some might not support cache coherence or might have
different memory models. ... In RISC-V systems, these properties and
capabilities of each region of the machine's physical address space are
termed physical memory attributes (PMAs)."
...
"Unlike physical memory protection values described in Section 3.7,
PMAs do not vary by execution context."
(specs/riscv-spec.html:75927-75954, anchor #pma / #norm:pma_indep_exec_context)

Mechanically the specification separates policy from checking into "a separate hardware structure, the PMA checker," whose attributes "in many cases ... are known at system design time ... and can be hardwired," while "where the attributes are run-time configurable, platform-specific memory-mapped control registers can be provided." The checking obligation is total: "PMAs are checked for any access to physical memory, including accesses that have undergone virtual to physical memory translation," and the specification "strongly recommend[s] that ... RISC-V processors precisely trap physical memory accesses that fail PMA checks," surfacing as "instruction, load, or store access-fault exceptions, distinct from virtual-memory page-fault exceptions." CVA6 realizes a static form of this: the attributes are expressed as configuration region rules rather than runtime MMRs, counted and legality- checked in core/include/config_pkg.sv (NrCachedRegionRules, NrExecuteRegionRules, NrNonIdempotentRules; asserted in check_cfg 451-453), and consulted in the load/store path (core/load_store_unit.sv) and the cache subsystem selected at core/cva6.sv:1400-1560. This links directly to the cache guide (a non-idempotent MMIO region must stay uncacheable end-to-end into any L2) and to the speculation guide (non-idempotent regions must not be speculatively accessed).

Pseudo-SystemVerilog synthesis notes

The implied structure is a post-translation attribute lookup that gates caching, execution, and atomics and raises a precise access fault:

module pma_checker #(
  parameter int unsigned NrCachedRegionRules,     // config_pkg::cva6_cfg_t
  parameter int unsigned NrExecuteRegionRules,
  parameter int unsigned NrNonIdempotentRules
)(
  input  logic [PLEN-1:0] paddr_i,        // checked AFTER VA->PA translation
  input  access_e         access_i,       // fetch / load / store / amo
  output logic            cacheable_o,    // -> D$/I$ + any external L2
  output logic            executable_o,
  output logic            idempotent_o,   // MMIO => 0 => no speculation/caching
  output logic            access_fault_o  // precise trap (recommended)
);
  // attributes are region-static (design-time), not per-context (contrast PMP)
endmodule
