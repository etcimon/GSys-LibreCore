Vol II §6.8 — Smctr Control Transfer Records Extension, Version 1.0

Canonical: specs/riscv-spec.html#smctr. Source line: specs/riscv-spec.html:85550. Domain: BP.

Smctr defines a hardware log of control-flow transfers (jumps, branches, calls, returns, traps, trap returns) exposed through CSRs for profiling and debugging. It requires the frontend to capture control-flow events and write them to a FIFO/buffer in program order, with filtering by privilege and mode. This is related to branch prediction because both must classify control-flow instructions, but CTR is an architectural record rather than a predictor.

Spec quotation

"The Smctr/Ssctr extensions provide a hardware mechanism to record
control transfers (branches, jumps, calls, returns, traps, and trap
returns) made by software. The recorded control transfers can be read
through a set of CSRs."
(specs/riscv-spec.html:85550-85555, anchor #smctr)

module smctr (
  input  logic        cf_event_i,     // branch/call/return/jump/trap

  output logic [XLEN-1:0] record_o,
  output logic        record_valid_o

  // record control transfers in-order; CSR-visible buffer
endmodule

CVA6 status: absent. No control-transfer record buffer or CTR CSRs exist in the core. Adding Smctr would tap the same branch/call/return classification logic as the branch predictor (core/frontend/frontend.sv:210-221) and add an in-order FIFO accessible to core/csr_regfile.sv.

.dts linkage: no DT node; Smctr/Ssctr would be advertised in the riscv,isa string if implemented.
