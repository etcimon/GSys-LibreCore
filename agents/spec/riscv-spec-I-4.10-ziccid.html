Vol I §4.10 — Ziccid Extension for Instruction/Data Coherence and Consistency

Canonical: specs/riscv-spec.html#_ziccid_extension_for_instructiondata_coherence_and_consistency. Domain: CACHE.

Ziccid mandates more stringent consistency between instruction fetches and other memory accesses then the base ISA. It guarantees that a hart's instruction fetches appear to occur in program order with respect to each other, and that stores eventually become visible to all harts' instruction fetches. In CVA6 the separate I$ and D$ are not hardware-coherent by default, so FENCE.I plus the D$ flush knobs are used as a manual substitute; full Ziccid would require either a coherent cache subsystem or automatic invalidation of I$ on D$ writes to code regions.

Spec quotation

"The Ziccid extension mandates more stringent requirements for
consistency between instruction fetches and other memory accesses than those
imposed by the base ISA. As described in detail in the next section, Ziccid
guarantees that a hart's instruction fetches appear to occur in program order
with respect to each other, and that stores eventually become visible to all
harts' instruction fetches."
(specs/riscv-spec.html:10665-10673, anchor #_ziccid_extension_for_instructiondata_coherence_and_consistency)

CVA6 status: partial; absent as automatic hardware coherence. FENCE.I is decoded in core/controller.sv:70-71,140-157,259 and stalls/flushs the frontend via core/frontend/frontend.sv:312-321. The optional D$ flush on FENCE.I is controlled by DcacheFlushOnFenceI declared in core/include/config_pkg.sv:214; the field's purpose is documented at core/include/config_pkg.sv:201-203 (required for write-back caches because data and instruction caches are currently not coherent). Most shipped target packages set it 1'b0 because the WT D$ is write-through; software must still execute FENCE.I to observe its own stores as instructions.

.dts linkage: memory@ nodes describing code regions must use the same address ranges as the CachedRegion/ExecuteRegion rules in the CVA6 config, so that FENCE.I plus any manual flush/invalidation operates on the intended coherent-cacheable regions.
