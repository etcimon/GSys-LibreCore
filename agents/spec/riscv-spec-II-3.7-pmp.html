Vol II §3.7 — Physical Memory Protection (PMP)

Canonical: specs/riscv-spec.html#pmp (source line 76569). Domain: RAM.

The objective of §3.7 is security and fault containment: to support secure processing and contain faults, it is desirable to limit the physical addresses accessible by software running on a hart. An optional physical memory protection (PMP) unit provides per-hart machine-mode control registers to allow physical memory access privileges (read, write, execute) to be specified for each physical memory region. The PMP values are checked in parallel with the PMA checks. The default permission model is the security primitive: PMP can grant permissions to S and U modes, which by default have none, and can revoke permissions from M-mode, which by default has full permissions.

(specs/riscv-spec.html:76569-76579, anchor #pmp)

Mechanically the specification fixes the checked scope and the register file. Checks "are applied to all accesses whose effective privilege mode is S or U, including instruction fetches and data accesses ... and data accesses in M-mode when the MPRV bit in mstatus is set and the MPP field ... contains S or U," and additionally "to page-table accesses for virtual-address translation, for which the effective privilege mode is S." Optional M-mode locking makes "the PMP registers themselves ... locked ... until the hart is reset." Enforcement is exact — "PMP violations are always trapped precisely." The register file is normative: "PMP entries are described by an 8-bit configuration register and one MXLEN-bit address register," "up to 64 PMP entries are supported," implementations "may implement zero, 16, or 64 ... the lowest-numbered PMP entries must be implemented first," all fields are WARL, and matching modes are TOR/NA4/NAPOT with lowest-index priority. CVA6 implements this in core/pmp/, with the pmpcfg*/pmpaddr* CSRs living in core/csr_regfile.sv; the check is wired into the fetch and load/store address paths. This links to the RAM guide (PMP + PMA must agree with the .dts map) and to the speculation guide (a precise PMP trap must not permit any speculative side effect to commit).

Pseudo-SystemVerilog synthesis notes

The implied structure is a priority-encoded matcher over up to 64 entries, evaluated in parallel with PMA and producing a precise fault:

module pmp #(parameter int unsigned NrEntries)(   // 0, 16, or 64
  input  logic [PLEN-1:0]  paddr_i,
  input  priv_lvl_e        priv_i,       // effective mode (MPRV/MPP aware)
  input  access_e          access_i,     // fetch/load/store
  input  logic [7:0]       pmpcfg_i  [NrEntries],  // R W X A(TOR/NA4/NAPOT) L
  input  logic [XLEN-1:0]  pmpaddr_i [NrEntries],  // core/csr_regfile.sv
  output logic             allow_o,
  output logic             access_fault_o          // always precise
);
  // lowest-numbered matching entry wins; locked entries bind M-mode too.
endmodule

CVA6 status: implemented (configurable entry count per target via CVA6Cfg.NrPMPEntries). CSR state is declared in core/csr_regfile.sv:300-301, output to the PMP unit at :339-340, and read at :857-960. Writes with lock/TOR checks are at :1839-1936 (pmpcfg) and :1866-1936 (pmpaddr). The PMP block is in core/pmp/src/pmp.sv:15-73, with per-entry matching in core/pmp/src/pmp_entry.sv:15- and TOR/NA4/NAPOT extraction. It is consumed by the instruction fetch port (core/pmp/src/pmp_if.sv) and the data port (core/pmp/src/pmp_data_if.sv:9-160), the latter instantiated in core/load_store_unit.sv:383-407. PMP violations raise precise access faults (INSTR_ACCESS_FAULT, LD_ACCESS_FAULT, ST_ACCESS_FAULT).

.dts linkage: PMP is an internal hart security mechanism and is not described by a DT node, but any memory@ / reserved-memory regions visible to PMP-aware software (OpenSBI/Linux pmp driver) must match the ranges configured by the firmware in pmpcfg/pmpaddr CSRs.
