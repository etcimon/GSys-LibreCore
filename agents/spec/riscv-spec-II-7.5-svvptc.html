Vol II §7.5 — Svvptc Extension for Obviating Memory-Management Instructions after Marking PTEs Valid

Canonical: specs/riscv-spec.html#ext:svvptc. Domain: RAM.

Svvptc allows software to make a PTE valid without executing an SFENCE.VMA/SINVAL.VMA afterward, provided the PTE was previously invalid and no stale translation existed. When the Svvptc extension is implemented, explicit stores by a hart that update the Valid bit of leaf and/or non-leaf PTEs from 0 to 1 and are visible to a hart will eventually become visible within a bounded timeframe to subsequent implicit accesses by that hart to such PTEs. It relaxes the normal page-table-modification ordering, reducing TLB shootdown overhead, but relies on cache/TLB coherency mechanisms to ensure stale entries cannot be used.

CVA6 status: absent. The MMU/TLB in core/cva6_mmu/cva6_mmu.sv and core/cva6_mmu/cva6_tlb.sv treats SFENCE.VMA / SINVAL.VMA as the only architecturally required synchronization for PTE modifications; there is no tracker that records "this PTE changed from invalid to valid by this hart" to skip an explicit fence. The page-table walker in core/cva6_mmu/cva6_ptw.sv reads PTEs from memory and installs them in the TLB, but it does not guarantee bounded visibility of a remote hart's 0→1 Valid-bit update without an SFENCE.VMA. Implementing Svvptc would require either TLB invalidation state tagging or a cache-coherency-based invalidation promise for PTE writes.

.dts linkage: no DT node; Svvptc capability would be reported through the CPU mmu-type or an ISA/property string and would require OS support to elide SFENCE.VMA after valid PTE stores.
